# Nav2 bringup

Runs the Nav2 2D navigation stack (Jazzy, navigation2 1.3.x) as a native systemd service on the client RPi 5:

```bash
ros2 launch nav2_bringup bringup_launch.py use_localization:=False \
  params_file:=/opt/ros2-lerobot-swerve-platform/nodes/nav2_bringup/config/nav2_params.yaml
```

`use_localization:=False` skips map_server and AMCL: the `map` frame and `/map` come from the separate
[slam_toolbox](../slam_toolbox/README.md) node (online async). `slam:=True` is not used, because bringup's SLAM
option requires localization and runs online_sync.

## Frames and inputs

- `map -> odom`: slam_toolbox. `odom -> base_link`: robot_localization_ekf. `base_link -> laser_frame`: static TF.
- Odometry: `/odometry/filtered` (bt_navigator, controller_server, velocity_smoother).
- Obstacles: `/scan_filtered` (RPLidar A1 with the robot's own body removed by `nodes/laser_filter`) in both costmaps and the collision monitor.
- Goals: `/goal_pose` (bt_navigator) or the `navigate_to_pose` action.

## Servers configured in `config/nav2_params.yaml`

`navigation_launch.py` starts all of these in one container; each has a section, because a server without its
params (notably collision_monitor and docking_server) fails to configure and aborts the lifecycle bringup.

| Server | Configuration |
|---|---|
| bt_navigator | `global_frame: map`, `robot_base_frame: base_link`, `odom_topic: /odometry/filtered`. |
| controller_server | MPPI, `motion_model: Omni`, `vx` +-0.25, `vy_max` 0.25 (symmetric in Jazzy), `wz_max` 0.5 rad/s, 10 Hz, `model_dt` 0.1, 30 steps, 1000 samples; holonomic critics (PathAngleCritic mode 1, TwirlingCritic, no PreferForwardCritic). |
| planner_server | `GridBased` = Smac state lattice (`nav2_smac_planner::SmacPlannerLattice`), omni primitives at 2.5 cm, footprint-aware; `allow_unknown: true` (plans into unexplored space while mapping), tolerance 0.5 m, `max_planning_time` 2 s. See [Global planner](#global-planner-smac-lattice). |
| global_costmap | `map` frame, 2.5 cm cells (= the SLAM map); static layer on `/map` (`map_subscribe_transient_local: true`), obstacle layer from `/scan_filtered` (footprint clearing off), inflation 0.35 m / `cost_scaling_factor` 24 (see [Penalty zone](#penalty-zone-inflation); mcp_server sets both at runtime for its footprint), no footprint padding, `initial_transform_timeout` 300 s (a deploy restarts nav2 before the gradual ramp brings up odom). |
| local_costmap | `odom` frame, 3 x 3 m rolling window at 2.5 cm (120 x 120 cells); obstacle layer from `/scan_filtered` (footprint clearing off), inflation 0.35 m / `cost_scaling_factor` 24, no footprint padding, `initial_transform_timeout` 300 s (a deploy restarts nav2 before the gradual ramp brings up odom). |
| footprint | The robot's real top-view H outline united with the parked arm's ground shadow (68-vertex non-convex polygon, rear notch; the front notch lies under the parked gripper) in both costmaps, generated by `scripts/gen_nav_footprint.py`. See [Footprint](#footprint). |
| behavior_server | spin / backup / drive_on_heading / assisted_teleop / wait; `local_frame: odom`, `global_frame: map`, rotation <= 0.5 rad/s. |
| smoother_server | SimpleSmoother. |
| velocity_smoother | open loop, `max_velocity [0.25, 0.25, 0.5]`, `min_velocity [-0.25, -0.25, -0.5]`, accel 1.0 m/s^2, 2.0 rad/s^2. |
| collision_monitor | `base_link` / `odom`, `cmd_vel_smoothed -> cmd_vel`; a direction-aware `stop` polygon `StopBox` (`velocity_polygon`): the H footprint swept 2 cm toward the commanded direction (generated), source `/scan_filtered`. `StopBox` is enabled (validated on the robot, see [Collision monitor](#collision-monitor)). A second polygon `ArmStop` (`approach`, direction-aware) takes its shape from mcp_server and is enabled only while the arm is released out of the static footprint (see [Dynamic footprint](#dynamic-footprint-arm-released)). |
| docking_server | One `SimpleChargingDock` plugin (a non-empty plugin list is mandatory) and no docks: it configures with an empty dock database and only accepts requests that carry an explicit dock pose. |
| waypoint_follower | WaitAtWaypoint. |
| route_server | `graph_filepath: ""`: configures with an empty graph ("No graph file provided to load yet"); a graph can be loaded later through its `set_route_graph` service. |

Velocity chain: controller/behaviors -> `cmd_vel_nav` -> velocity_smoother -> `cmd_vel_smoothed` ->
collision_monitor -> `/cmd_vel` (unstamped Twist) -> swerve_drive_controller.

## Footprint

The costmaps use the robot's real outline from above, an H: the two side frames (x +-0.2125, y +-0.1158..0.1508,
35 mm wide, measured 2026-10-10), the crossbar (x -0.15..0.10, y +-0.1158, up to the frames' inner faces), the four
steering wheel envelopes (circles r 0.0625 m around the steer axes at (+-0.1525, +-0.1333): the 120 x 35 mm wheel turns
so it can point anywhere and sweeps the circle of its half-diagonal) and the lidar dome (measured diameter 74 mm, r 0.037 m, centred at (0.150, 0.040); it stands in front of the crossbar, 13 mm
clear of it, and its front x 0.187 is behind the frames' front x 0.2125; the `laser_frame` TF at (0.158, 0.06) is the
calibrated scan origin and is not the dome position). Their union is one counter-clockwise, simple (no self-intersection), non-convex polygon of 67 vertices,
430 x 392 mm overall, with a front notch (between the front wheels, ahead of the crossbar; the lidar dome stands in it) and a
rear notch (between the rear wheels, behind the crossbar). `footprint_padding` is 0: every wheel and lidar circle is
approximated by a 16-gon that circumscribes it (1.2 mm overshoot for 6 cm), so the outline never cuts into the real
envelope. Gaps narrower than 2 x `close_gap_m` (2 cm) between parts are filled: no obstacle fits there and they would
only add vertices (this closes the 13 mm slit between the lidar dome and the crossbar). The old footprint was a 370 x 286 mm rectangle, smaller than the wheel envelope.

The static footprint also contains the arm parked at its stored home: the folded arm's gripper overhangs the crossbar
front to x 0.32 (above the front notch), ~10 cm beyond the body outline. The generator unions the ground shadow of
`parked_arm_joints` (scripts/gen_nav_footprint.yaml; computed with mcp_server's arm model, grown and simplified by
5 mm) into the H, so the costmaps, the StopBox and the laser_filter polygon all cover the parked gripper (68 vertices,
max x 0.3225; circumscribed radius 0.33 m).

Non-convex footprints in Nav2 Jazzy (checked in the navigation2 1.3.13 sources and a Docker run, see
[Validation](#validation-in-docker)):

- Costmap footprint cost (`nav2_costmap_2d::FootprintCollisionChecker::footprintCost`, used by MPPI's `CostCritic`
  with `consider_footprint: true`, the Smac `GridCollisionChecker` and the behavior server) rasterises the outline
  edges only, so the notches are free space. The inscribed (0.100 m, nearest edge) and circumscribed (0.268 m,
  farthest vertex) radii come from `calculateMinAndMaxDistances`, valid for any simple polygon.
- collision_monitor tests points with a ray-crossing point-in-polygon (`Polygon::isPointInside`), valid for any simple
  polygon.
- The one consumer that assumes convexity is ObstacleLayer footprint clearing: `setConvexPolygonCost` fills the
  footprint column by column (`Costmap2D::convexFillCells`) and would erase real obstacles in the notches. It is
  switched off on both costmaps (`footprint_clearing_enabled: false`); the robot's own returns are already removed by
  the laser_filter self polygon, and raytracing clears stale cells.

### Dynamic footprint (arm released)

The footprint above is the static one, loaded from the params at startup. mcp_server replaces it at runtime while the
arm is released out of it (`release_control(subsystem='arm', keep_position=true[, carried_object_radius_m])`, a human
moving the released arm, an mcp_server restart with the arm out): the footprint becomes the static outline + the
measured arm's ground shadow (+ a circle of the carried object's radius at the tool point), recomputed every 5 s from
the live pose; without fresh joint states a conservative max-reach disc around the arm mount. `take_control('arm')`, a
parked release and a converged `/arm/home` publish the static outline again (details: `nodes/mcp_server/README.md`,
"Navigation footprint").

| Consumer | How it follows |
|---|---|
| local / global costmap | `Costmap2DROS` subscribes its relative `footprint` topic (`geometry_msgs/Polygon`, SystemDefaults QoS): mcp_server publishes on `/local_costmap/footprint` and `/global_costmap/footprint`. The costmaps re-publish it on `<costmap>/published_footprint` (global frame), which the behavior server and docking server read and mcp_server compares with its footprint. `footprint_padding` stays 0 (mcp_server already includes the margins it wants). |
| costmap inflation | mcp_server sets `inflation_layer.inflation_radius` (circumscribed radius rounded up to a cell) and `inflation_layer.cost_scaling_factor` (steepest that keeps cost >= 1 at the circumscribed radius, at most 25) on `/local_costmap/local_costmap` and `/global_costmap/global_costmap` with every footprint change (dynamic InflationLayer parameters); a bigger footprint would otherwise outgrow the inflation and MPPI / Smac would check the full footprint at every pose. The static footprint restores the generated values. |
| collision_monitor `StopBox` | Does not follow: Jazzy reads `velocity_polygon` sub-polygons once at configure and has no footprint topic for them. It keeps covering the static footprint. |
| collision_monitor `ArmStop` | `type: polygon`, `action_type: approach` (`time_before_collision` 1 s, `simulation_time_step` 0.05 s), no static `points`: its shape arrives on `polygon_sub_topic` `/collision_monitor/arm_stop_polygon` (`PolygonStamped`, `polygon_subscribe_transient_local: true`); `enabled: false` at startup. mcp_server publishes the part of the arm shadow + carried circle outside the static footprint grown by `stopbox_margin_m` (2 cm, the StopBox sweep) and sets `ArmStop.enabled` true (the parameter is dynamic in Jazzy); static footprint (also a released arm inside it): false. Checked in Docker with navigation2 1.3.13 (2026-10-11): "Polygon points are not defined. Using dynamic subscription instead", the shape update arrived, `ArmStop.enabled true` accepted. `approach` slows down only toward an obstacle next to the arm, so the robot can back away from it (a `stop` polygon zeroed every command). |
| laser_filter | Its `polygon` parameter is set to the footprint + 1 cm (see `nodes/laser_filter/README.md`). |

A restarted Nav2 falls back to the static footprint and inflation from these params: its `published_footprint` then
differs from mcp_server's footprint, and the next 5 s tick republishes the footprint and inflation to that costmap
only. An unchanged footprint is not re-sent (each footprint change re-inflates the whole costmap). A consumer whose
`set_parameters` service comes back gets its values within 0.5 s.

### Changing body numbers

All derived geometry (footprint, inflation radius, StopBox sub-polygons, laser_filter polygon) comes from one body
model. Its source is the mcp_server `body:` block in `ansible/group_vars/client.yml` (the arm self-collision model:
`boxes` with centre/size and `cylinders` with x, y, radius, z range in `base_link`) when present, else the `body:` in
`scripts/gen_nav_footprint.yaml`. The script also writes the geometry numbers mcp_server's dynamic footprint uses
(`nav_footprint:` in the mcp_server config of `client.yml`) and shares its outline code with mcp_server
(`nodes/mcp_server/mcp_server/footprint_geometry.py`). After changing a number, regenerate and commit the files:

```bash
uv run python scripts/gen_nav_footprint.py
uv run pytest tests/test_nav_footprint.py tests/test_nav_stack_config.py -q
```

The script only rewrites the regions between `# >>> gen_nav_footprint: <name>` and `# <<< gen_nav_footprint: <name>`
markers; `tests/test_nav_footprint.py` fails while the committed files differ from its output.

## Penalty zone (inflation)

The penalty zone around obstacles is as small as the footprint-aware checks allow. `inflation_radius` is the
circumscribed radius rounded up to a cell (0.3295 -> 0.35 m, the parked gripper's tip): MPPI and Smac only check the full footprint where the
centre cost reaches the cost at the circumscribed radius, so inflation must reach it (they log an error otherwise).
`cost_scaling_factor` is the steepest falloff up to `max_cost_scaling_factor` 25 that keeps the cost >= 1 at the
circumscribed radius: ln(252) / (0.3295 - 0.100) = 24.1, rounded down to 24.0 (cost 252 at the 0.10 m inscribed radius,
1/4 of it 6 cm out). The formula lives in `nodes/mcp_server/mcp_server/footprint_geometry.py`; mcp_server applies it
to every footprint it publishes. Both costmaps use the same values. The old setup (rectangle footprint, 0.24 m at
factor 10) kept a much wider band of high cost; now the planner can pass a 0.42 m doorway with a 0.392 m wide robot.

## Global planner (Smac lattice)

NavFn planned a point and relied on inflation to keep the body clear, which cannot express an H. The `GridBased`
planner (name kept, so the BT `compute_path` and the web UI keep working) is now Smac's state lattice planner: each
expansion is a precomputed motion primitive and is collision-checked with the full rotated footprint near obstacles.
Settings: `allow_unknown: true`, `tolerance` 0.5 m (as NavFn), `max_planning_time` 2 s, `cost_penalty` 2.0 (the
lattice's counterpart of SmacPlanner2D's `cost_travel_multiplier`: moderate, keeps paths off obstacles without long
detours), `rotation_penalty` 5.0, analytic expansion ratio 3.5 / max length 3 m / max cost 200,
`cache_obstacle_heuristic: true` (the BT only replans when the path becomes invalid), no reverse expansion (not
applicable to omni). The package comes with `ros-jazzy-nav2-bringup` (it depends on `ros-jazzy-navigation2`, which
depends on `ros-jazzy-nav2-smac-planner`), so no new apt package is needed.

### Lattice primitives

`config/lattice/output.json` (128 primitives, 16 headings, omni: arcs plus sideways slides and in-place rotation by
one heading bin) was generated with Nav2's own generator from the jazzy branch
(`nav2_smac_planner/lattice_primitives/generate_motion_primitives.py`, navigation2 commit
`645abd95f2be02a13ca539b29c2ddc065db34f89`, version 1.3.13) with `config/lattice/config.json`:

```json
{"motion_model": "omni", "turning_radius": 0.5, "grid_resolution": 0.025, "stopping_threshold": 5, "num_of_headings": 16}
```

Nav2 ships primitives only at 5 cm, and the primitives' `grid_resolution` must equal the costmap resolution. To
regenerate (e.g. after a resolution change):

```bash
git clone --depth 1 --branch jazzy https://github.com/ros-navigation/navigation2.git /tmp/navigation2
uv venv /tmp/latvenv --python 3.12
VIRTUAL_ENV=/tmp/latvenv uv pip install -r /tmp/navigation2/nav2_smac_planner/lattice_primitives/requirements.txt
cd /tmp/navigation2/nav2_smac_planner/lattice_primitives
/tmp/latvenv/bin/python generate_motion_primitives.py \
  --config <repo>/nodes/nav2_bringup/config/lattice/config.json \
  --output <repo>/nodes/nav2_bringup/config/lattice/output.json \
  --visualizations /tmp/lattice_vis
```

`lattice_filepath` is the absolute path of the robot checkout (`ros2_repo_dest`, `/opt/ros2-lerobot-swerve-platform`).
0.5 m turning radius: the swerve base can turn in place and slide sideways, so the arcs only shape smooth turns.

## CPU and memory cost of 2.5 cm

The RPi 5 is ~80% busy, so the costs (watch the Robot SLAM dashboard and the nav2 / slam_toolbox unit CPU after
deploy):

- Costmaps: 4x the cells. Local 3 x 3 m window 14 400 cells (was 3 600), global = map area / 6.25 cm^2 (4x). The
  inflation pass, raytracing (2x cells per ray) and `costmap_raw` / `costmap` messages grow accordingly.
- Footprint checks: the H outline is ~2.0 m of edges = ~80 cells per check (the old rectangle 1.3 m at 5 cm = 26
  cells), done per MPPI sample point only near obstacles (centre cost above the circumscribed cost) and per Smac
  expansion near obstacles.
- Smac lattice vs NavFn: in Docker on the M4 a ~5 m plan took 2-4 ms, ~7 m through a doorway 4-8 ms (36 ms through a
  0.42 m doorway); expect several times that on the RPi 5, still far below the 2 s `max_planning_time`. Replans only
  happen when the path becomes invalid.
- SLAM: see [slam_toolbox](../slam_toolbox/README.md#map-resolution) (raster every 10 s instead of 5 s to compensate).

## Validation in Docker

No ROS on the dev machine, so the params file was loaded by the real Jazzy servers in an arm64 `ros:jazzy` image with
`ros-jazzy-navigation2`, `ros-jazzy-nav2-bringup` and `ros-jazzy-laser-filters` (navigation2 1.3.13, laser_filters
2.0.10), the repo mounted at `/opt/ros2-lerobot-swerve-platform`: map_server with a synthetic 10 x 4 m map at 2.5 cm
(a wall across the middle with a doorway), static TFs, planner_server, controller_server, collision_monitor,
behavior_server under a lifecycle manager, and the laser_filter chain. Result (2026-10-10): every server configured and
activated without errors (MPPI: "Critic will collision check based on footprint cost", no inflation warning; Smac:
"Using motion model: State Lattice"); plans through a 0.60, 0.45 and 0.42 m doorway succeed, a 0.35 m doorway (narrower
than the robot) fails with "no valid path found"; the laser_filter removed a return on the side frame and kept returns
in the front and rear notch.

## Rotate first, drive front-first

`FollowPath` is the `RotationShimController` wrapping MPPI. When a new path points more than 45 deg away from the robot heading, it first rotates in place (0.5 rad/s) until within about 17 deg, then MPPI follows the path. At the end, once inside the goal tolerance, the shim alone turns to the goal heading (`rotate_to_heading_once`, `max_angular_accel` 0.5). MPPI's `GoalAngleCritic` is off because the two fought. The measured 58 deg overshoot had one cause: the default BT replans at 1 Hz and every replan resets the goal checker latch and the shim's position check, so the shim lost the in-tolerance state mid-turn and MPPI took over. `GoalCritic` (weight 8) brings the robot close before the turn. MPPI's `PathAngleCritic` runs in mode 0 (forward preference, weight 4.0), so the robot keeps its front toward the direction of travel instead of strafing. Why: the lidar is partly covered at the back and on the right, so it sees best ahead.

## Goal tolerance

Goals finish within 1 cm and 2 deg (`xy_goal_tolerance` 0.01, `yaw_goal_tolerance` 0.035, stateful). This needs three things together: the BT `navigate_w_recovery_and_replanning_only_if_path_becomes_invalid.xml` (mid-route replanning only on an invalid path, so the latch holds), `PoseProgressChecker` (rotation counts as progress; radius 0.05 m, angle 0.3 rad, 20 s allowance), and the shim settings above. Short sideways goals (a few cm) rotate 90 deg toward the path first (front leading) and then turn back to the goal heading.

## Keepout and speed zones

Zones drawn as POIs become two costmap filters, fed by `nodes/costmap_zones` (keepout and speed masks plus latched `CostmapFilterInfo` on `/costmap_filter_info/keepout` and `/costmap_filter_info/speed`).

- **KeepoutFilter** (`keepout_filter`) is in `plugins` of both costmaps, directly before `inflation_layer`, so the zone is inflated like an obstacle (Smac's centre-cost shortcut needs that). Mask cells are lethal; cost 252 (`override_lethal_cost`, below lethal so inflation does not grow it) is written only while the robot is inside a zone, so it can plan a way out.
- **SpeedFilter** (`speed_filter`) is in `filters` of the local costmap only and publishes `/speed_limit` (absolute topic); `controller_server.speed_limit_topic` is the same topic.
- Requirements: Nav2 1.3.8 for the KeepoutFilter lethal override and 1.3.10 for live mask updates (a changed or cleared mask repaints the costmap without a restart); older builds ignore `override_lethal_cost` or keep stale zones.
- Kill switch: each filter layer serves a `toggle_filter` (`std_srvs/SetBool`) service in its costmap node's namespace; calling it with `data: false` disables that filter at runtime without a redeploy.
- Limits: the `RotationShimController` in-place rotation is not limited by `/speed_limit` (only MPPI translation and rotation while following the path are). `route_server` `AdjustSpeedLimit` stays idle because no route graph is loaded.

## Collision monitor

collision_monitor always runs and sits in the velocity chain (`cmd_vel_smoothed -> cmd_vel`). Its body polygon,
`StopBox` (the footprint swept 2 cm toward the motion, stop on 4+ points), is `enabled: true`: it reads `/scan_filtered`, where
`nodes/laser_filter` has removed the lidar returns on the robot body. A 20 s stationary sample on the robot
(2026-10-03) found 0 returns in the 5 cm band. Without the filter the raw `/scan` had ~130 self-hits inside the
footprint, which would have zeroed `cmd_vel` permanently. Disable at runtime with
`ros2 param set /collision_monitor StopBox.enabled false`.

`StopBox` is a holonomic `velocity_polygon`: it only stops motion toward an obstacle. The command direction
(`atan2(vy, vx)`) picks one sub-polygon: `forward`, `back`, `left` or `right` within 10 deg of an axis, and the
diagonal sectors in between. Each is the H footprint swept 2 cm over every direction of its sector (Minkowski sum of
the footprint with the sector, 68-71 vertices, generated by `scripts/gen_nav_footprint.py`), so a return stops the
robot only when the part of the body facing it moves toward it, and nothing is added on the side it moves away from.
An obstacle deep in a notch stops no translation; one just ahead of the crossbar stops only forward motion. Near-zero
linear speed (`rotate`, below 0.005 m/s, which includes rotating in place) checks the bounding box + 2 cm, because a
turning H sweeps its corners and its notches. A robot stopped next to a wall can still back away or slide along it. A
plain stop polygon zeroed every command once a return was inside, so the robot froze against the wall.

### Validating StopBox on the robot (after changing the lidar, filter or footprint)

1. Put the robot in open space (nothing within ~0.5 m) with rplidar_a1, static_tf_publisher and nav2_bringup running.
2. Check that `/scan` has no returns inside the StopBox `rotate` polygon (the largest one). The lidar sits at
   `x=0.158, y=0.06, yaw=pi` in `base_link` (static TF `base_link -> laser_frame`). On the client:

   ```bash
   source /opt/ros/jazzy/setup.bash
   python3 - <<'PY'
   import math
   import rclpy
   import yaml
   from rclpy.qos import qos_profile_sensor_data
   from sensor_msgs.msg import LaserScan

   PARAMS = "/opt/ros2-lerobot-swerve-platform/nodes/nav2_bringup/config/nav2_params.yaml"
   LASER_X, LASER_Y, LASER_YAW = 0.158, 0.06, math.pi   # base_link -> laser_frame
   stop = yaml.safe_load(open(PARAMS))["collision_monitor"]["ros__parameters"]["StopBox"]
   POLY = yaml.safe_load(stop["rotate"]["points"])

   def inside(x: float, y: float) -> bool:
       hit, j = False, len(POLY) - 1
       for i, (xi, yi) in enumerate(POLY):
           xj, yj = POLY[j]
           if (yi > y) != (yj > y) and x < (xj - xi) * (y - yi) / (yj - yi) + xi:
               hit = not hit
           j = i
       return hit

   rclpy.init()
   node = rclpy.create_node("stopbox_check")
   hits = []

   def on_scan(msg: LaserScan) -> None:
       for i, r in enumerate(msg.ranges):
           if not (msg.range_min <= r <= msg.range_max):
               continue
           a = msg.angle_min + i * msg.angle_increment + LASER_YAW
           x, y = LASER_X + r * math.cos(a), LASER_Y + r * math.sin(a)
           if inside(x, y):
               hits.append((round(math.degrees(a)), round(r, 3)))

   node.create_subscription(LaserScan, "/scan", on_scan, qos_profile_sensor_data)
   for _ in range(50):                # ~5 s of scans at the A1's ~10 Hz
       rclpy.spin_once(node, timeout_sec=0.2)
   print(f"{len(hits)} returns inside StopBox (angle deg, range m):", sorted(set(hits))[:40])
   PY
   ```

   Returns inside the footprint itself are the body (removed by the laser_filter from `/scan_filtered`); returns
   between the footprint and the box edge are self-hits the filter misses, or real obstacles in the notches.
   Any return here is a self-hit. Do not enable StopBox until it is gone: mask the obstruction, shrink the polygon
   only if it stays outside the footprint (change `stopbox_margin_m` in `scripts/gen_nav_footprint.yaml` and regenerate), or raise `min_points` above the number of self-hit points per scan.
3. With zero self-hits, enable it at runtime and watch the state topic while driving a Nav2 goal in open space:

   ```bash
   ros2 param set /collision_monitor StopBox.enabled true
   ros2 topic echo /collision_monitor_state   # must stay silent / action_type 0 in open space
   ros2 topic echo /cmd_vel                   # must follow /cmd_vel_smoothed while the goal runs
   ```

   Then walk up to the robot: `/collision_monitor_state` must report the `stop` action and `/cmd_vel` drop to zero
   only while something is inside the box.
4. Make it permanent: set `StopBox.enabled: true` in `config/nav2_params.yaml`, keep `tests/test_nav_stack_config.py`
   in sync (it pins the disabled default), commit and redeploy nav2_bringup.

If Nav2 goals plan but the robot never moves, check `/collision_monitor_state` first: a stuck `stop` action means a
self-hit inside an enabled polygon.

## Plan topics (for visualization)

- **Global plan**: `/plan` (`nav_msgs/Path`, frame `map`), published by planner_server for every computed path.
- **Local plan**: `/optimal_trajectory` (`nav_msgs/Path`, frame `odom` = local costmap frame). In Jazzy the
  controller_server itself publishes no local plan; the MPPI controller's `TrajectoryVisualizer`
  (`nav2_mppi_controller/src/trajectory_visualizer.cpp`) publishes the optimal trajectory of each control cycle on
  `optimal_trajectory` (relative to the un-namespaced controller_server, hence `/optimal_trajectory`) only when
  `FollowPath.visualize: true`, which is set here. It also publishes `/trajectories` (MarkerArray of candidate rollouts)
  and `/transformed_global_plan` (Path); every one of these is only built and sent when it has a subscriber, so
  leaving `visualize` on costs nothing while nobody watches.

The web UI Map tab (`ansible/group_vars/client.yml`, tab `map`) uses `/plan` and `/optimal_trajectory`.

## Tuning

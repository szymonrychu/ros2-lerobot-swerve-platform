# laser_filter

Removes RPLidar returns and head D435 cloud points that hit the robot itself, so SLAM, the Nav2 costmaps (lidar obstacle layer and D435 voxel layer `depth_voxel_layer`), the collision monitor, web_ui and mcp_server do not treat the robot body (or the released arm and a carried object) as an obstacle.

**Audience:** Mid-level Python dev with ROS2.

- **Node:** the repo Python node `laser_filter` (`python3 -m laser_filter`, rclpy), launched by Ansible as `laser_filter` on the client with `LASER_FILTER_CONFIG=<repo>/nodes/laser_filter/config/footprint_filter.yaml`.
- **Topics:** subscribes `scan_topic` `/scan` (RPLidar, frame `laser_frame`, sensor-data QoS), publishes `scan_filtered_topic` `/scan_filtered` (reliable, depth 10). The D435 cloud `/head/d435/points` -> `/head/d435/points_filtered`: see "D435 cloud self filter".
- **Filter:** every beam whose point (range x cos / sin of its angle, in the scan frame) lies inside the self polygon becomes NaN; every other range (also inf / NaN) is kept. The polygon is given in `polygon_frame` (`base_link`) and transformed once into the scan frame (the lidar mount is a static TF: x, y of R (x, y, 0) + t, as laser_filters' `StaticLaserScanPolygonFilter` does; the TF quaternion becomes a rotation matrix with plain numpy, `quaternion_matrix`, no scipy); the point test is shapely `contains_xy` on the prepared polygon, valid for non-convex polygons. Scans are dropped (not published) until the TF `polygon_frame -> scan frame` is known: no unfiltered scan ever reaches `/scan_filtered`.
- **Startup polygon:** the static footprint (H body + the arm parked at its stored home) grown by 1 cm, generated by `scripts/gen_nav_footprint.py` from the same body model as the Nav2 footprint and the collision monitor StopBox (see `nodes/nav2_bringup/README.md`, "Footprint"); do not edit it by hand. Returns inside the rear notch (between the rear wheels, behind the crossbar) are real obstacles and are kept; the front notch lies under the parked gripper. There is no padding parameter: the margin is generated into the polygon (laser_filters padded by moving each vertex by `sign(x)`, `sign(y)`, which shrinks a non-convex outline at the notch walls).
- **Runtime polygon:** parameter `polygon` (string `"[[x, y], ...]"` in `polygon_frame`), starting at the config polygon. Setting it through the parameter service (`ros2 param set /laser_filter polygon "[[...]]"`) replaces the polygon at once (the cached transform is kept); an invalid value (not a string; not a list of at least three numeric `[x, y]` pairs; a NaN / inf coordinate; a self-intersecting or zero-area polygon, with which `contains_xy` would silently filter nothing) is refused with the reason and the current polygon stays (`apply_polygon_param`, the node's set-parameters callback). mcp_server sets it to its navigation footprint + 1 cm: the dynamic footprint (static outline + released arm shadow + carried object) while the arm is released out of the static outline, the static one otherwise. It re-sends it every 5 s and, after a restart of this node (which starts from the static config polygon), within 0.5 s of the parameter service coming up (`nodes/mcp_server/README.md`, "Navigation footprint").
- **Why not laser_filters:** the node used to be laser_filters' `scan_to_scan_filter_chain` with `StaticLaserScanPolygonFilter`. laser_filters 2.0.10 (Jazzy) cannot change a polygon filter's polygon at runtime: the chain declares `filter1.params.polygon` read-only, and the filter's reconfigure callback and `footprint_topic` subscription live on the filter's own node, which nothing spins (upstream issue #231). Checked in Docker (2026-10-11, `ros-jazzy-laser-filters` 2.0.10): the chain parameter set fails with "read-only", the filter node's parameter service never answers, and a polygon on the footprint topic changes nothing. The repo node was checked in the same image (numpy 2.4.3 venv over the system packages, as deployed): a return on the startup polygon was removed and one outside kept, a `SetParameters` call (as mcp_server sends it) replaced the polygon and every return inside the new one was removed, an invalid polygon was refused.
- **Why filter at all:** on the robot the lidar sees parts of the platform 0.22-0.24 m from the sensor. slam_toolbox's `min_laser_range` (0.15 m) does not remove them, so without the filter they become occupied cells around the robot and the planner can only plan to the robot's own position.

## D435 cloud self filter

The head D435 cloud (`d435_obstacle_cloud`, rtabmap_util `point_cloud_xyz` on head_rgbd_cpp's edge-masked full-FOV D435 depth) sees the robot body, the parked gripper, the released arm and a carried object whenever the head looks down. The same node removes those points with the same runtime `polygon`, so mcp_server's dynamic footprint (released arm shadow, carried object) applies to the cloud without a second parameter target.

- **Topics:** subscribes `cloud_topic` `/head/d435/points` (sensor-data QoS), publishes `cloud_filtered_topic` `/head/d435/points_filtered` (reliable, depth 5: reaches reliable and best-effort subscribers). Consumers: `ground_estimator_cpp`, the Nav2 local costmap D435 voxel layer (`depth_voxel_layer`, STVL), the collision monitor depth sources (`depth_obstacles`, `depth_cliff`), the web_ui 3D obstacles layer and mcp_server's obstacle summary. `cloud_topic: null` disables the cloud path (no subscription, publisher or timer).
- **Frame and stamp kept:** the output is an xyz float32 cloud (`sensor_msgs_py.point_cloud2`, apt `ros-jazzy-sensor-msgs-py`) with the input header unchanged: same `frame_id` (`d435_depth_optical_frame`), same capture stamp. The kept points are not moved; consumers transform them with the TF at that stamp.
- **Filter:** each point is transformed into `polygon_frame` (`base_link`) with the TF `polygon_frame <- cloud frame` at the cloud's stamp (`transform_points`), and removed when its (x, y) lies inside the current self polygon (shapely `contains_xy` on the prepared polygon, valid for the non-convex H) and its z <= `cloud_self_max_height_m` (1.0 m) (`cloud_self_mask`). Points above the limit over the robot (an overhang), points in the front and rear notch and points below the floor outside the polygon (cliffs) are kept. Non-finite points are removed.
- **TF at the stamp, never cached:** the head pans and tilts, so every cloud looks up its own transform at its header stamp (unlike the scan's static transform, which is cached).
- **Non-blocking:** the lookup is `tf2_ros` `wait_for_transform_async` (timeout 0): answered at once when the TF at the stamp is there, otherwise a future the TF listener completes the moment the TF arrives. Scan filtering is never delayed by a cloud TF wait. A cloud without its TF waits in one newest-wins slot (`PendingSlot`): a newer cloud replaces it, and a 50 ms expiry timer drops it once it waited longer than `cloud_transform_timeout_s` (0.2 s). A newer cloud that gets its TF first also drops the waiting older one (no out-of-order output).
- **Drop counting:** every dropped cloud (no TF in time, superseded, TF lookup error, older than a published one) is counted, and a warning throttled to one per 5 s logs the reason and the running count (`N clouds dropped so far`).
- **No placeholder data:** nothing is published for a cloud without TF at its stamp, never an unfiltered or untransformed cloud, and no timer publishes (the expiry timer only drops). An input cloud with zero points (a real frame with no valid returns) is published as an empty cloud with its real header once its TF is there: it truthfully says "no returns" and keeps the collision monitor's freshness check meaningful.
- **Checked in Docker** (2026-10-18, `ros:jazzy-ros-base`, sensor_msgs_py 5.3.8): with the deployed config and a head TF, a cloud with TF at its stamp came out with the same frame and stamp and only the notch, cliff and overhang points; a cloud ahead of the TF was published the moment the TF arrived; a cloud whose TF never came was dropped after 0.2 s and counted; of two clouds waiting for TF only the newer was published; an empty cloud came out empty with its header; `/scan_filtered` kept working.

## Config (`config/footprint_filter.yaml`, pydantic `LaserFilterConfig`, unknown keys rejected)

| Key | Default | Meaning |
|---|---|---|
| `executor` | `single_threaded` | `events` runs the node on `rclpy.experimental.EventsExecutor` (far less Python executor overhead; deployed on the client); `single_threaded` is the classic executor. Rollback: set `executor: single_threaded` in `group_vars/client.yml` and redeploy the node. The node creates no callback group and uses no MultiThreadedExecutor semantics, so the EventsExecutor ignoring callback groups changes nothing |
| `scan_topic` | `/scan` | raw scan |
| `scan_filtered_topic` | `/scan_filtered` | filtered scan |
| `polygon_frame` | `base_link` | frame of the polygon |
| `transform_timeout_s` | 0.1 | longest TF wait per scan before it is dropped (only until the static TF is known) |
| `polygon` | required | startup self polygon (generated region) |
| `cloud_topic` | `/head/d435/points` | raw D435 cloud (`d435_obstacle_cloud`); `null` disables the cloud path |
| `cloud_filtered_topic` | `/head/d435/points_filtered` | D435 cloud without the robot's own points (input frame and stamp) |
| `cloud_self_max_height_m` | 1.0 | points inside the polygon with z <= this (m, `polygon_frame`) are the robot; > 0 |
| `cloud_transform_timeout_s` | 0.2 | longest wait for the TF at a cloud's stamp before it is dropped and counted; > 0 |
| `metrics_port` | `null` | Prometheus `/metrics` on 127.0.0.1 (shared `ros2_metrics`); `null` falls back to `METRICS_PORT`, else off. Deployed: 19120 |

## Stall telemetry (`metrics.py`)

Added after the 2026-10-22 16:30:35 invalid-source stop, when both outputs stopped for ~1.9 s and nothing stored could
say which side stalled (nodes/nav2_bringup/README.md, "Invalid source stop during the final turn"). One executor timer
every 0.05 s records its own gap, refreshes the open scan gaps and expires the pending cloud.

| Metric | Meaning |
|---|---|
| `laser_filter_scan_gap_seconds{stream}` (histogram) and `_max` (gauge) | time between consecutive scans: `stream="input"` is `/scan` reaching `on_scan`, `"output"` is `/scan_filtered` after publish. `_max` is the longest gap of the last 60 s including the open gap since the latest scan |
| `laser_filter_scan_lag_seconds{stream}` and `_max` | wall clock minus the scan header stamp at the same points |
| `laser_filter_executor_tick_gap_seconds` and `_max` | time between executor ticks (a stalled executor) |

Buckets 0.05-5 s; the `le="1.0"` bucket splits gaps at the collision monitor `source_timeout`.

## Code layout

| Module | ROS? | Purpose |
|---|---|---|
| `self_filter.py` | no | `parse_polygon` (finite, valid simple polygon), `apply_polygon_param` (runtime parameter: replace or refuse), `quaternion_matrix`, `transform_points`, `cloud_self_mask` (cloud point keep mask), `PendingSlot` (newest-wins cloud waiting for TF, drop count), `SelfFilter` (transform, runtime polygon replacement, beam test, `filter_cloud`) |
| `config.py` | no | pydantic config, `LASER_FILTER_CONFIG` |
| `metrics.py` | no | stall telemetry: `create_families`, `GapLagWindow` (gap and lag histograms, 60 s window max), `LaserFilterMetrics` (input, output, executor tick) |
| `node.py` | yes | `LaserFilterNode`: `polygon` parameter with validation, TF lookup, scan in / out, D435 cloud in / out (non-blocking TF at the stamp, pending slot), the 0.05 s tick (executor gap, open scan gaps, cloud expiry), metrics server start |
| `__main__.py` | yes | entry point |
